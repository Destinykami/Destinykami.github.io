# Mem0 2026

官方blog地址：https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm

2026 年 Mem0 的一个重大变化，是放弃原来的 ADD / UPDATE / DELETE 写入流程，改为：

$$ \boxed{\text{Single-Pass Extraction + ADD-only}} $$
## 1. 旧版 Mem0 的问题

2025 年的流程：

```
Conversation
     │
     ▼
LLM Extraction
     │
     ▼
Candidate Memories
     │
     ▼
Vector Search
     │
     ▼
LLM Update Decision
     │
     ├── ADD
     ├── UPDATE
     ├── DELETE
     └── NOOP
     │
     ▼
Memory Store
```

其中至少涉及两个主要 LLM 阶段：

$$ C_{\text{write}} \approx C_{\text{extract}}+C_{\text{update}} $$

并且 UPDATE、DELETE 可能破坏历史信息。

新版 Mem0 认为，这两个问题可以一起解决。

## 2. 新版 Mem0：Single-Pass ADD-only

新版的基本流程是：

```
Conversation
     │
     ▼
Retrieve Related Memories
     │
     ▼
Single LLM Extraction
     │
     ▼
Deduplication
     │
     ▼
Entity Linking
     │
     ▼
ADD Memories
```

这里有一个容易忽略的细节：

ADD-only 不代表完全不参考已有记忆，新版写入时依然会先检索相关的旧记忆，用来为一次 LLM 提取提供去重上下文。但是，LLM 不再负责执行复杂的 UPDATE / DELETE 决策，提取后的事实会经过批量 Embedding、基于 Hash 的精确去重等处理，再写入数据库。


这样会产生大量矛盾，这正是新版Mem0要解决的问题，**ADD-only 将一部分复杂性从写入时的冲突处理，转移到了检索时的状态判断。**

我们已经有：

```
M1：玩家喜欢弓箭。
M2：玩家不喜欢弓箭。
M3：玩家重新喜欢弓箭。
```

如果用户问：

> 玩家现在喜欢弓箭吗？

单纯按照 Semantic Similarity 检索，这三条记忆可能都有很高的相似度。

这是一种设计取舍：

|维度|旧版 Mem0|新版 Mem0|
|---|---|---|
|写入|提取后决定增删改|单次提取，主要新增|
|历史保留|可能被覆盖|保留状态变化|
|写入 LLM 成本|两个主要阶段|一个主要阶段|
|检索|语义检索为主|多信号检索|
|主要挑战|错误更新、信息丢失|冗余积累、历史与当前状态区分|

Mem0 官方称，新版使记忆提取延迟大约降低一半。但这不等于整个 Agent 的端到端延迟降低一半。

## 3. Temporal Reasoning：怎样解决新旧状态的问题？

新版Mem0 为记忆增加时间相关元数据，包括：

- 事件发生时间；
- 事件是否仍然有效；
- 时间信息的精确程度；
- 记忆类型；
- 用于关联同一变化状态的 State Key。

当新的状态出现时，可以结束旧状态的有效期，但保留旧记忆本身。检索时，再根据查询所指的时间对相关记忆重新排序。

## 4. Mem0 Dream

它的核心思想是：**将长期记忆的整理维护与用户实时交互解耦。**

Dream 主要处理三类操作。

|操作|含义|示例|
|---|---|---|
|Merge|合并信息重复或被完整包含的记忆|将重复的偏好记录归并|
|Supersede|标记旧事实已经被新事实取代|玩家从骑士团转入魔法师协会|
|Synthesize|根据多条独立记忆生成高层认知|玩家多次帮助 NPC → NPC 逐渐信任玩家|

这里有一个实现细节：官方文档描述的 Merge 和 Supersede 判断可在提取阶段进行，而 Synthesize 是按计划在后台运行的。

## 5. 有待解决的问题

新版 Mem0 的官方实验报告：

| Benchmark   | 旧版    | 新版    |
| ----------- | ----- | ----- |
| LoCoMo      | 71.4% | 92.5% |
| LongMemEval | 67.8% | 94.4% |
此外，新算法在大规模记忆场景中仍存在明显不足。

例如，Mem0 官方公布的 BEAM 10M 测试结果：

|能力|正确率|
|---|---|
|Preference Following|90.4%|
|Knowledge Update|75.0%|
|Multi-session Reasoning|26.1%|
|Temporal Reasoning|16.3%|
|Event Ordering|20.2%|
|Contradiction Resolution|32.5%|

这些数据显示：**当历史达到千万 Token 级别时，跨会话推理、事件排序以及时序推理依然非常困难。**

## 6. 思考：ADD-only 是否真的解决了 Memory Update？

假设 NPC 的记忆库有 100 万条记忆。

其中关于玩家武器偏好的记忆就有 1000 条：

```
M1：玩家喜欢弓箭。
M2：玩家喜欢长剑。
M3：玩家喜欢法杖。
...
M998：玩家喜欢长剑。
M999：玩家不喜欢长剑。
M1000：玩家喜欢弓箭。
```

玩家现在问：

> 你还记得我现在最喜欢什么武器吗？

系统使用新版 Mem0 的 Semantic + BM25 + Entity Matching 检索。

> **BM25（Best Matching 25）是一种经典的基于关键词匹配的文本检索算法**，广泛用于搜索引擎和信息检索系统。

**思考两个问题：**

**问题 1：** 即使采用 ADD-only，为什么仍然可能检索到错误的历史状态？Semantic、BM25、Entity Matching 能否从根本上解决这个问题？
> ADD-only 虽然避免了覆盖或删除历史事实导致的信息丢失，但也会使同一实体的多个历史状态同时存在。
> Semantic Search 只能衡量语义相关性，BM25 主要衡量关键词匹配程度，Entity Matching 负责关联相关实体。这三者都没有显式建模事实的时间有效性，因此无法从根本上解决历史状态冲突。
> 

**问题 2：** 如果在新版 Mem0 上设计一个专门针对游戏 NPC 的 Memory Retrieval 模块，怎样确保当前状态查询优先返回最新有效事实，同时仍然能够回答历史问题？

> 简单增加 Recency Weight 也不够，因为最新记忆不一定是查询需要的记忆，而且写入时间不一定等于事件发生时间。
> 更合理的方案是引入 Temporal Memory，为持续性事实建立 State Key 和有效时间区间，并通过 Query Temporal Intent 判断是查询当前状态还是历史状态，最后结合时间约束进行检索或重排序。
